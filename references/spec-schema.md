# 规格（spec）字段说明

规格是**唯一**能被执行的输入。它只描述"发什么请求、判什么条件"，不描述业务背景——业务背景留在用例表里。

一份最小可跑规格：

```json
{
  "name": "登录接口用例",
  "spec_version": "1.0",
  "env": "test",
  "base_url": "http://10.31.0.101",
  "api_prefix": "/common/idaas/v1",
  "auth": {"type": "header", "header": "app-sec-at", "token_env": "AUTOTEST_TOKEN"},
  "vars": {"tenantId": "1001"},
  "cases": [
    {
      "id": "TC-AUTH-001",
      "模块": "认证",
      "用例标题": "有效 token 通过校验接口",
      "优先级": "P0",
      "自动化": "auto",
      "依据": "登录态探活是所有接口用例的前置。",
      "steps": [
        {
          "名称": "调用 tokenValid",
          "method": "GET",
          "path": "/auth/tokenValid",
          "断言": [
            {"类型": "状态码", "等于": 200},
            {"类型": "成功标志", "等于": true}
          ]
        }
      ]
    }
  ]
}
```

## 顶层字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 规格名，进报告标题 |
| `spec_version` | 建议 | 改了断言就升版本，回归对比时能对上是哪版 |
| `env` | 否 | 默认环境档名，可被 `--env` 覆盖 |
| `base_url` | 是* | 协议 + 域名 + 端口，不带结尾斜杠 |
| `api_prefix` | 否 | 所有接口的公共前缀，如 `/api/v1` |
| `auth` | 是* | 认证配置，见 `auth-adapters.md` |
| `vars` | 否 | 全局变量，供 `${var}` 引用 |
| `environments` | 否 | 内联环境档，优先用外部 `environments.json` |
| `timeout` | 否 | 单请求超时秒数，默认 15 |
| `verify_tls` | 否 | 内网自签证书设为 `false` |
| `需求` | 否 | 需求清单，作为覆盖度分母。`["R-01"]` 或 `[{"id":"R-01","说明":"…"}]`。不写则分母退化为「用例里出现过的需求点」 |
| `contract` | 否 | API 响应契约配置：内置 Schema 或本地 OpenAPI 3 JSON。只有步骤显式写「响应契约」才生效，不能替代业务断言。 |
| `virtual_services` | 否 | 仅 loopback 内存替身数组。必须显式声明 `name` 与 `routes`；运行时只注入 `${virtual.<name>.base_url}`。见下节。 |
| `observability` | 否 | DB/MQ/Trace 只读观测 DSL。只允许测试专用 HTTP 网关和预声明来源；不接受 SQL、MQ 命令、TraceQL 或任何后端直连配置。见下节。 |

`*` 标的两项若在环境档里给出，规格里可以省略——同一份规格跑多环境就靠这个。

### 虚拟依赖与故障注入

`virtual_services` 只能启动绑定 `127.0.0.1` 随机端口的内存 HTTP 服务；它不会修改 DNS、代理、hosts 或任何真实网络。被测系统必须由**自身的测试配置**显式指向变量注入的替身地址，执行器不会重定向真实依赖：

```json
{
  "autotest": {"mode":"isolated", "allow_hosts":["127.0.0.1"], "allow_virtualization":true},
  "virtual_services": [{
    "name":"payment",
    "routes":[{"match":{"method":"GET","path":"/charge"},
               "response":{"status":200,"json":{"ok":true}}}]
  }],
  "cases":[{
    "id":"TC-DEP-001", "模块":"支付", "用例标题":"上游 503 被妥善处理",
    "steps":[{
      "名称":"安装当前步骤的支付故障", "method":"GET",
      "path":"${virtual.payment.base_url}/charge",
      "故障":{"服务":"payment", "match":{"method":"GET","path":"/charge"},
              "action":"response", "response":{"status":503,"json":{"down":true}}},
      "断言":[{"类型":"状态码","等于":503}]
    }]
  }]
}
```

- `name` 必须唯一；每个 `routes` 项都要有精确的 `match.method`、`match.path` 和响应。故障规则也只能精确匹配已声明 route，避免宽泛规则影响其他请求。
- `path` 使用 `${virtual.<name>.base_url}` 时才允许访问替身；普通绝对 URL 会被拒绝，不能借虚拟化访问真实网络。
- 步骤 `故障` 仅支持 `delay`（非负 `毫秒`）、`response`（显式响应）和 `reset`；规则在步骤请求前安装、步骤结束立即移除，作用域只有当前步骤。
- 故障步骤必须有断言或 `DB` / `MQ` / `Trace` 观测。若规则未命中，或隔离模式、主机白名单、`autotest.allow_virtualization=true` 任一条件缺失，该用例稳定记为 `blocked`，而不是产品失败。
- `result.json` 的 `steps[].virtual` 会记录服务名、规则、作用域、每次命中与是否触发，便于核对故障确实发生。运行结束（即使认证、执行或报告异常）始终停止所有虚拟服务。

## 只读观测：DB / MQ / Trace

观测只通过项目提供的**测试专用只读 HTTP 网关**执行。执行器只会 `GET <base_url>/query`，
并固定携带 `source`、`run_id`、`case_id`、`step_id`；网关必须回显这三个相关性 ID，且返回
`read_only:true`、`truncated:false`。任一条件不满足、网关不可用或结果截断都稳定归类为
`blocked`，绝不会把不可观测误判成产品或规格问题。

```json
{
  "autotest": {"mode":"isolated", "allow_hosts":["127.0.0.1"], "allow_observation_gateway":true},
  "observability": {
    "gateway": {"base_url":"http://127.0.0.1:9300", "timeout_ms":3000},
    "sources": {
      "orders_db": {"kind":"DB"},
      "order_events": {"kind":"MQ"},
      "order_trace": {"kind":"Trace"}
    }
  },
  "cases": [{"id":"TC-ORDER-011", "模块":"订单", "用例标题":"提交后落库并发事件", "steps":[{
    "名称":"提交订单", "method":"POST", "path":"/orders",
    "观测等待": {
      "来源":"orders_db",
      "直到":{"类型":"DB", "来源":"orders_db", "数量":{"大于等于":1}},
      "超时":30000, "间隔":1000
    },
    "断言":[
      {"类型":"状态码", "等于":201},
      {"类型":"DB", "来源":"orders_db", "数量":1, "字段":{"status":"CREATED"}},
      {"类型":"MQ", "来源":"order_events", "事件类型":"OrderCreated"},
      {"类型":"Trace", "来源":"order_trace", "错误数":0}
    ]
  }]}]
}
```

- `gateway` 只支持 `base_url`、`timeout_ms`；`sources.<名称>` 只支持 `kind: DB|MQ|Trace`。compile/lint 会拒绝 `sql`、`command`、`traceql` 等未知字段，防止借 DSL 直连后端。
- 使用观测前必须显式启用隔离策略：`autotest.mode=isolated`、网关主机在 `allow_hosts` 中、`allow_observation_gateway:true`。安全策略或网关不可用均为 `blocked`。
- `观测等待` 在步骤业务断言前运行；`直到` 可写一条或数组 DB/MQ/Trace 断言。条件在超时前不成立为 `failed`，因为这是可用观测下的规格未满足；不可用、截断、非只读则为 `blocked`。
- `result.json.steps[].observability` 只保存记录数与最多三条已脱敏安全摘要，原始记录不会落盘；报告会展示等待次数、结果与安全摘要。
- 网关的查询能力必须由部署方预声明。**禁止**在规格中写 SQL、消息消费/管理命令、TraceQL、数据库/MQ/追踪平台连接串或凭据。


| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一，建议 `TC-模块-序号`，`--only` 按前缀筛 |
| `模块` | 是 | 报告按它分组 |
| `用例标题` | 是 | 模块内唯一，描述"期望的正确行为" |
| `优先级` | 建议 | P0/P1/P2 |
| `自动化` | 是 | `auto` 或 `manual`；`manual` 会跳过执行并单列 |
| `依据` | 建议 | 为什么这样判，失败时帮人判断是否真是缺陷 |
| `失败即止` | 否 | 默认 `true`；横切类用例设 `false`，一次跑完全部步骤 |
| `依赖` | 否 | 依赖的用例 id 列表；依赖未通过则本条 `skipped` |
| `重试` | 否 | 失败后重跑次数，默认 0。重试后通过会被标为 `flaky` |
| `vars` | 否 | 用例级变量，覆盖同名全局变量 |
| `数据` | 否 | 数据驱动：对象数组，一行一组参数；执行时展开成多条。见下节 |
| `需求点` | 否 | 本条验证的需求 ID，字符串或数组；可标多个。见 `result-and-triage.md` 的覆盖度口径 |
| `setup` / `teardown` | 否 | 前置造数 / 后置清理，格式同 `steps`；`teardown` 无论成败都执行 |
| `steps` | 是 | 步骤数组 |
| `缺陷等级` | 否 | 如 `高｜语义不一致`，只用于报告分组，不影响判定 |

### 数据驱动：一行一组参数

```json
{"id":"TC-ORDER-007","用例标题":"不同金额下单的返回码","模块":"订单",
 "数据":[{"金额": 0,   "预期": 400},
         {"金额": 0.01,"预期": 200},
         {"金额": 99999,"预期": 200}],
 "steps":[{"名称":"下单","method":"POST","path":"/order",
           "json":{"amount":"${金额}"},
           "断言":[{"类型":"状态码","等于":"${预期}"}]}]}
```

规则：

- **展开成 N 条**，id 加 `#1`、`#2`…，`用例标题` 保持不变（报告分组与缺陷归并都靠它）
- 数据行的键写进 `vars`，**优先级高于用例级 `vars`**；没被行覆盖的公共变量继续生效
- `数据` 不收标量：`[1, 2, 3]` 或 `{"a":1}` 都会在 lint / 编译期报错。要传标量就写成 `[{"值": 1}]`
- 空数组也是错：不用数据驱动就删掉这个键（空数组意味着"一条都不跑"，静默丢用例比报错更糟）
- 请求体里 **整串引用保留类型**：`"${金额}"` 得到数字 `0`，`"${开关}"` 得到布尔 `true`；
  嵌在别的字符串里（`"order-${金额}"`）仍按字符串拼接
- `依赖` 写基础 id（`TC-X`）时要求**它展开的每一行都通过**；写 `TC-X#2` 只判那一行，
  行号越界在 lint 期报错
- 报告「总览」多一行「数据驱动展开 N 行（来自 M 条用例）」，明细每行注明「数据组 2/5：金额=…」
- 数据里**不要放真实密码/密钥**：它原样进 `result.json` 与报告

选择原则：**同一段步骤逻辑、只有参数不同**才用 `数据`。步骤本身也要变（比如一组走接口、一组走页面），
那是两条用例，硬塞进数据组只会让报告难读。

### 需求覆盖：把「跑过的」对回「需求」

```json
{"需求":[{"id":"R-01","说明":"登录失败三次锁定"},
         {"id":"R-02","说明":"订单导出"}],
 "cases":[{"id":"TC-AUTH-003","模块":"登录","用例标题":"连续错三次被锁定",
           "需求点":["R-01"],"steps":[]},
          {"id":"TC-ORDER-010","模块":"订单","用例标题":"导出当月订单",
           "需求点":["R-02","R-01"],"steps":[]}]}
```

口径（报告与 `result.json` 的 `coverage` 块都按这个算）：

- **分母**是 `需求` 声明的条数；没声明时退化成「被引用到的需求点」，结果里标 `declared_source: "observed"`，报告的措辞会跟着变成「不说明需求清单完整」
- 一条需求的状态取它**所有关联用例里最差**的那个：`failed > blocked > skipped > manual > passed`。有一条失败，整条需求记失败
- 只有关联用例**全部通过**才算「已验证」；只有 `manual` 用例记「仅人工」——人工和未执行都不算测过了
- 一条用例都没关联 → `uncovered`，与「失败」分开统计：一个是没写用例，一个是写了没过
- `--only` / `--fail-fast` 时结果标 `partial_run`，报告注明「只代表所选范围」，这种数字不能当全量覆盖汇报
- `需求点` 引用了 `需求` 里没有的 ID 会在编译期报错：拼错一个字母，覆盖度会静默变低，而报告毫无异常

## 步骤字段

**两类步骤**：没有 `ui` 键的走 HTTP，有 `ui` 键的走浏览器。它们产出同形状的响应，断言和提取完全共用。

### HTTP 步骤

| 字段 | 说明 |
|---|---|
| `名称` | 出现在失败信息里，写清"在做什么" |
| `method` | GET/POST/PUT/DELETE/PATCH |
| `path` | 以 `/` 开头，与 `api_prefix` 拼接 |
| `params` | query 参数对象，自动编码；也可直接写进 `path` |
| `json` | JSON 请求体 |
| `form` | 表单请求体（`application/x-www-form-urlencoded`） |
| `body` | 原始字符串体 |
| `headers` | 额外请求头，会与认证头合并 |
| `no_auth` | `true` 表示这条请求不带认证头（测未授权场景） |
| `断言` | 断言数组 |
| `提取` | `{"变量名": "JSON路径"}`，供后续步骤引用 |
| `timeout` | 覆盖单步超时 |
| `文件` | 上传的文件：路径、路径数组，或 `{字段名: 路径}`。配了就走 multipart |
| `下载目录` | 把响应体存成文件，落到这个目录；不给则落到 `<输出目录>/下载` |
| `轮询` | 反复请求直到条件成立，见下面「轮询」一节 |

### 上传与下载：把文件真的传上去、存下来

**HTTP 上传**走 multipart。`form` 里的普通字段会和文件一起发：

```json
{"名称": "上传合同", "method": "POST", "path": "/contract/upload",
 "form": {"bizType": "lease"},
 "文件": {"file": "/Users/me/合同.pdf"},
 "断言": [{"类型": "JSON字段", "路径": "data.fileId", "非空": true}]}
```

| 写法 | 效果 |
|---|---|
| `"文件": "/abs/a.pdf"` | 单文件，字段名 `file` |
| `"文件": ["/a.pdf", "/b.pdf"]` | 多文件，都挂在 `file` 下 |
| `"文件": {"avatar": "/a.png", "docs": [...]}` | 显式字段名 |

文件不存在时**当场报错**，不会发一个没有文件的空请求（那会让服务端返回 400，
却被记成「接口缺陷」）。文件名里的中文原样发出去。

**HTTP 下载**给 `下载目录`，响应体会落盘，产物描述进响应的 `downloads`：

```json
{"名称": "导出报表", "method": "GET", "path": "/report/export",
 "params": {"month": "2026-09"},
 "下载目录": "/tmp/导出",
 "断言": [{"类型": "下载", "后缀": ".xlsx", "最小字节": 1024}]}
```

文件名优先取 `Content-Disposition`（含 `filename*=UTF-8''…`），拿不到就用 URL 末段。
同名文件会加 `(2)` 序号，不互相覆盖。路径穿越（`../../etc/passwd`）被剥成纯文件名。

**UI 通道**见 `ui-adapters.md` 的 `上传` / `下载` 两个动作。

### 轮询：等异步状态落地

异步接口（提交后生成订单、设备上线、报表跑完）不要用 `{"毫秒": 3000}` 硬等 ——
等短了假失败，等长了每条用例都慢。用 `轮询`：

```json
{"名称": "等设备上线", "method": "GET", "path": "/device/${deviceId}/status",
 "轮询": {"直到": {"类型": "JSON字段", "路径": "data.online", "等于": true},
          "超时": 30000, "间隔": 1000},
 "断言": [{"类型": "JSON字段", "路径": "data.registered", "等于": true}],
 "提取": {"onlineSince": "data.onlineSince"}}
```

| 字段 | 说明 |
|---|---|
| `直到` | 一条断言或断言数组，**全部成立**即结束。复用 14 类断言的写法 |
| `超时` | 总预算毫秒，默认 30000；写 `0` 表示只试一次 |
| `间隔` | 两次请求的间隔毫秒，默认 1000，下限 50 |
| `method`/`path`/`params`/`json`/`form`/`headers`/`no_auth` | 可选，覆盖步骤上的同名字段 |

行为约定：

- 条件成立**立刻**往下走，不把剩余预算等完
- 最后一次响应就是本步骤的响应，`提取` 与 `断言` 都基于它 ——
  「等状态变成已支付，再把订单号提出来」写成一步即可
- 超时才算失败，失败信息带最后一次的实际值（如 `最后一次 data.online=false`）
- 中途的 5xx / 连接异常**不立即判失败**，继续轮询；
  一次都没拿到响应时按通道阻断（`blocked`）处理，不记成产品缺陷
- `直到` 写错（缺判定条件、引用未定义变量）在编译期就报出来

**只能用在 HTTP 步骤上。** UI 步骤等异步渲染请用 `等待`：

```json
{"ui": "点击", "选择器": "#submit",
 "等待": {"选择器": ".result-row", "状态": "visible", "超时": 8000}}
```

### UI 步骤

| 字段 | 说明 |
|---|---|
| `ui` | 动作名：`点击` `填写` `选择` `按键` `等待` `悬停` `滚动到` `切换frame` `断言快照` `识别验证码` |
| `选择器` | CSS 或 Playwright 选择器，支持 `${变量}` |
| `值` | 填写/选择/按键时的值，支持 `${变量}` |
| `path` / `url` | 有就先导航。`path` 与 **`base_url`（不含 `api_prefix`）** 拼接；`url` 用绝对地址 |
| `等待` | `{"选择器":"...","超时":8000}` 等元素出现/消失；`{"毫秒":800}` 硬等 |
| `等网络空闲` | 导航后是否等 `networkidle`。`false` 可关掉（个别系统在 idle 之后才取验证码） |
| `网络空闲超时` | `networkidle` 的超时毫秒数，默认 8000。超时不算失败，只记诊断 |
| `第几个` | 选择器命中多个时选第 N 个（从 0 起） |
| `超时` | 覆盖本步骤超时（毫秒） |

`ui` 动作细节、等待纪律、选择器策略见 `ui-adapters.md`。**断言与提取字段与 HTTP 步骤相同。**

UI 步骤特有行为：

- 失败时自动整页截图，路径写进 `result.json` 的 `steps[].screenshot`
- 动作失败 → `failed`（页面行为不符）；导航失败 → `blocked`（环境问题）
- 提取额外支持 `text:正则`（从页面文本抓）与 `元素:选择器`（取该元素的文本或值）
- **导航的主文档 HTTP 状态码会被记录**，`状态码` 断言对**发生导航的** UI 步骤有效。
  没有导航的步骤（点击、填写）**没有状态码**，对它写 `状态码` 断言会报规格错误 ——
  见下面「状态码」一节。
  若导航返回 4xx/5xx 而步骤没写 `状态码` 断言，执行器会自动补一条前置检查判失败——
  因为页面都没打开，后面任何断言都不成立。这条检查排在自有断言之前，先暴露根因。
- `result.json` 里 UI 步骤的 `status` 可能是 `null`（= 没导航），别按整数比较
- `steps[].diagnostics` 记录采集/等待环节的异常（截图没存成、监听器没挂上等），
  **不影响判定**，但意味着本轮证据可能不完整

## 断言类型全表

判定条件的键和值一一对应，**一条断言只判一件事**。

> 后四类（`页面` / `URL` / `控制台` / `网络`）只对 UI 步骤生效。挂在 HTTP 步骤上会直接判"规格错误"，不会静默通过。

### 状态码

```json
{"类型": "状态码", "等于": 200}
{"类型": "状态码", "不等于": 500}
{"类型": "状态码", "在": [200, 204]}
```

**UI 步骤上要小心**：它读的是「这一步有没有导航、导航回了什么码」。

| 步骤 | 状态码断言的命运 |
|---|---|
| HTTP 步骤 | 真实响应码，永远可判 |
| UI 步骤 + `url`/`path`（有导航） | 主文档状态码，可判 |
| UI 步骤 + 只有 `ui` 动作（没导航） | **规格错误**，提示改用 `页面`/`URL`/`网络` |

第三行是刻意这么做的：早先版本对没导航的步骤返回 200，那条断言恒为真 ——
写了等于没写，还会让人以为验过了。

### 耗时

```json
{"类型": "耗时", "小于": 3000}
```

单位毫秒。只用来卡"明显不合理"，不要拿来卡严格的 SLA。

### 成功标志 / 业务状态

业务层自研状态码很常见（HTTP 恒 200，成败看 body）：

```json
{"类型": "成功标志", "等于": true}
{"类型": "业务状态", "等于": 0}
{"类型": "业务状态", "不等于": 0}
```

### JSON字段

```json
{"类型": "JSON字段", "路径": "data.total", "等于": 13}
{"类型": "JSON字段", "路径": "data.total", "不等于": 0}
{"类型": "JSON字段", "路径": "data.total", "期望在": [1, 50]}
{"类型": "JSON字段", "路径": "data.total", "大于等于": 1}
{"类型": "JSON字段", "路径": "data.total", "小于等于": 500}
{"类型": "JSON字段", "路径": "data.records.0.id", "是字符串": true}
{"类型": "JSON字段", "路径": "data.records", "是数组": true}
{"类型": "JSON字段", "路径": "data.enabled", "是布尔": true}
{"类型": "JSON字段", "路径": "data.pageNo", "是整数": true}
{"类型": "JSON字段", "路径": "data.records", "非空": true}
{"类型": "JSON字段", "路径": "data.records", "长度": 5}
{"类型": "JSON字段", "路径": "user.mobile", "正则": "^1\\d{2}\\*{4}\\d{4}$"}
```

路径支持数组下标（`records.0.id`）。

**数量断言一律优先用 `期望在`。** 写死 `等于 13` 的用例，环境加了一条数据就变红，两周后没人再看这份报告。

### 包含 / 不包含

对**整个响应体文本**做子串判断，适合文案、错误码、信息泄漏检查：

```json
{"类型": "包含", "值": "1-500"}
{"类型": "包含", "值": ["待处理", "INC"]}
{"类型": "不包含", "值": ["java.lang", "nested exception", "Failed to convert"]}
```

`不包含` 是安全类用例的主力断言：越权、泄漏、调试信息外泄都能用它卡住。

### 响应头

```json
{"类型": "响应头", "名称": "Content-Type", "包含": "application/json"}
{"类型": "响应头", "名称": "Cache-Control", "正则": "no-store"}
```

### 响应契约

响应契约用于系统地验证 **HTTP 响应** 的状态码、`Content-Type` 与 JSON 结构；它不验证请求参数，也不能替代「当前用户只能看自己的订单」这类业务断言。它只能挂在 HTTP 步骤，引用错误会在 `compile` / `lint` 阶段拦下；拿到真实响应后结构不符则判 `failed`。

最小、零依赖的内置 Schema 写法：

```json
{
  "contract": {
    "schemas": {
      "UserResponse": {
        "type": "object",
        "required": ["success", "data"],
        "properties": {
          "success": {"type": "boolean"},
          "data": {"type": "object", "required": ["id", "name"],
                   "properties": {"id": {"type": "integer"}, "name": {"type": "string"}}}
        }
      }
    }
  },
  "cases": [{"steps": [{"method": "GET", "path": "/users/me", "断言": [
    {"类型": "响应契约", "schema": "UserResponse", "状态码": 200, "内容类型": "application/json"}
  ]}]}]
}
```

也可引用**本地 OpenAPI 3 JSON**（`file` 相对规格文件所在目录；首版不读取 URL，也不支持 YAML）：

```json
{
  "contract": {"sources": {"public-api": {"type": "openapi3", "file": "contracts/openapi.json"}}},
  "cases": [{"steps": [{"method": "GET", "path": "/users/42", "断言": [
    {"类型": "响应契约", "来源": "public-api", "operationId": "getUser", "响应": "200"}
  ]}]}]
}
```

- 内置模式使用 `schema`；OpenAPI 模式必须同时使用 `来源`、`operationId`、`响应`，两种模式互斥。
- 支持的 Schema 子集：`type`、`required`、`properties`、`additionalProperties`、`items`、`minItems` / `maxItems`、`minLength` / `maxLength` / `pattern`、`minimum` / `maximum`、`enum`、`const`、本地 `#/...` `$ref`、OpenAPI 3 的 `nullable`。
- `result.json` 的步骤检查会追加 `contract.violations`（最多 20 条），但不会写入完整响应体；旧报告仍可读 `actual` 字段。
- HTTP 未连通仍是 `blocked`；不要把「没有响应」误报为「字段缺失」。

### 并发结果

`并发结果` 只能用于带 `并发` 配置的 HTTP 步骤，聚合判定有限次数的竞态或幂等请求：

```json
{"并发":{"请求数":10,"并发度":5,"总超时":8000,
          "幂等":{"header":"Idempotency-Key","value":"order-${__run_id}","模式":"共享"}},
 "断言":[{"类型":"并发结果","请求数":10,"成功数":10,
            "状态码":{"全部在":[200,201]},
            "JSON字段":{"路径":"data.orderId","去重数":1,"非空":true}}]}
```

并发写请求必须在 `autotest.mode=isolated`、主机白名单和 `allow_concurrency_writes=true` 的隔离环境中执行；上限为 50 个请求。它验证响应收敛，不单独证明数据库只写入一条，后者应使用测试专用观测网关的 `DB` 断言。

### 路径存在

```json
{"类型": "路径存在", "路径": "data.records.0.id"}
```

字段必须存在（值可以是空字符串），用于卡"字段被悄悄删掉"这类破坏性变更。

### 页面

```json
{"类型": "页面", "选择器": "h2", "文本": "我的应用"}
{"类型": "页面", "选择器": ".el-message--error", "可见": true}
{"类型": "页面", "选择器": "tbody tr", "数量": 10}
{"类型": "页面", "选择器": ".form-error", "数量": 0}
{"类型": "页面", "选择器": "input[name=user]", "值": "zrgj"}
{"类型": "页面", "选择器": "button.submit", "可用": true}
{"类型": "页面", "选择器": "img.logo", "属性": {"alt": "logo"}}
{"类型": "页面", "选择器": "h1", "文本等于": "用户登录"}
{"类型": "页面", "选择器": "body", "不含文本": ["系统错误", "500"]}
```

判定条件：`存在` / `可见` / `数量` / `文本`（包含）/ `文本等于` / `不含文本` / `值` / `属性` / `可用`。

**「查失败」不会写成「不存在」**。如果探测元素时页面正在跳转、iframe 被卸载、渲染卡住，
这条断言会报「无法判定」并给出原因，而不是判「元素不存在」——后者会产出一条假缺陷。
遇到这种情况给该步骤配 `等待.选择器`，等元素就绪再断言。

**`数量` 与 `可见` 不能混用**：
- `数量: 0` 判 DOM 里没有这个节点 —— 适合"校验提示未出现"
- `可见: false` 判节点存在但隐藏 —— 适合"弹窗关闭但 DOM 还在"

### URL

```json
{"类型": "URL", "包含": "/home"}
{"类型": "URL", "正则": "/detail/\\d+"}
```

判跳转是否正确。登录类用例几乎必须配一条（"没跳走"往往比"报了什么错"更能说明问题）。

### 控制台

```json
{"类型": "控制台", "无错误": true}
{"类型": "控制台", "不含": ["ResizeObserver loop"]}
```

采集 JS 的 `console.error` 和未捕获异常。**这是接口测试完全看不见的一类缺陷来源。**

采集是**累积的**（从会话打开到当前步骤），语义是"到目前为止页面出过错"。只想判某一步范围时，把它写成用例的最后一步。

已知无害的报错用 `不含` 精确排除，别整体关掉这条断言。

### 网络

```json
{"类型": "网络", "无失败请求": true}
{"类型": "网络", "无失败请求": true, "允许": ["favicon", "/static/png/"]}
```

采集状态码 ≥400 的响应和请求失败。`允许` 是 URL 片段白名单，用来放行 favicon、埋点、已知会给 404 的探测请求。

同样**只放固定 URL 片段进白名单**，否则这条断言就退化成永远通过。

判「某个接口到底调没调、调了几次、传了什么」用请求级断言：

```json
{"类型": "网络", "请求": "/api/order/submit", "次数": 1}
{"类型": "网络", "请求": "/api/order/submit", "方法": "POST", "次数": 1}
{"类型": "网络", "请求": "/api/user/list", "次数": {"小于等于": 2}}
{"类型": "网络", "请求": "/api/order/submit", "请求体包含": "\"source\":\"h5\""}
```

| 字段 | 说明 |
|---|---|
| `请求` | URL 片段（子串匹配） |
| `方法` | 可选，`GET`/`POST`… 不区分大小写 |
| `次数` | 整数（等于）或 `{大于: 1}` / `{大于等于: 1}` / `{小于: 2}` / `{小于等于: 2}` / `{不等于: 0}` |
| `请求体包含` | 一个或多个片段，全部命中才算通过；只对记录到的请求体前 500 字符判 |

两条边界：

- **只统计本步骤期间发出的请求**。同一个用例里前面步骤也调了同一接口，不会把
  `次数: 1` 顶成 2（按会话累积统计会把正常行为报成缺陷）
- 写这类断言的步骤，快照前会先等这一步的请求出现再等它安静（预算默认 3 秒，
  用步骤的 `网络空闲超时` 调），避免把「还没发出去」读成「0 次」
- 请求记录触顶（默认 500 条，规格 `ui.network_limit` 可调）时，
  `次数` / `请求体包含` 会**拒绝判定**并说明原因，不会给一个基于截断数据的结论

### 下载

判的是**磁盘上真实落下的那个文件**，不是接口返回了什么。

```json
{"类型": "下载", "后缀": ".xlsx"}
{"类型": "下载", "名称包含": "月度报表", "最小字节": 1024}
{"类型": "下载", "数量": 1}
{"类型": "下载", "最大字节": 10485760}
```

| 字段 | 说明 |
|---|---|
| `后缀` | 带不带点都行，大小写不敏感 |
| `名称包含` | 文件名子串 |
| `最小字节` / `最大字节` | 文件大小区间，用来挡「下到一个 0 字节的空壳」 |
| `数量` | 整数或 `{大于等于: 1}` 之类的条件 |
| `存在` | `true` 要求文件真的在磁盘上；`false` 断言不该产生文件 |

只判**最后一份**产物（同一用例里先下模板再下数据时，判的是数据那份），`数量` 判的是总数。

前提是该步骤真的下载过：UI 步骤要写 `{"ui":"下载",…}`，HTTP 步骤要写 `"下载目录"`。
两者都没有时编译期就报错 —— 没有产物就没有可判的东西。

四种情况会**拒绝判定**而不是给结论：

- 下载内容超过单文件上限（200 MB）没落盘 —— 截断的文件能骗过「最小字节」
- 下载触发了但保存失败（磁盘满、权限）—— 没文件就没法判
- 浏览器通道不可用
- 步骤没有下载动作

## 变量与提取

```json
{"名称": "查第一页", "method": "GET", "path": "/app/my-app",
 "params": {"pageNo": "1", "pageSize": "2"},
 "提取": {"firstId": "data.records.0.id", "total": "data.total"}}

{"名称": "查第二页", "method": "GET", "path": "/app/my-app",
 "params": {"pageNo": "2", "pageSize": "2"},
 "断言": [{"类型": "JSON字段", "路径": "data.records.0.id", "不等于": "${firstId}"}]}
```

提取来源：

| 写法 | 取值 |
|---|---|
| `data.id` | 响应 JSON 路径 |
| `status` | HTTP 状态码 |
| `header:Set-Cookie` | 响应头 |
| `cookie:SESSION` | Cookie 罐 |
| `text:(\\d+)` | 从页面/响应文本里正则抓第 1 个分组（UI 步骤常用） |
| `元素:.row .id` | 取该元素的文本或值（UI 步骤） |
| `captcha:data.base64Image` | 把该路径的 base64 图片**直接 OCR 成文本**（详见下节） |

`${变量}` 可用于 `path`、`params`、`json`、`form`、`headers`、断言值。

### `captcha:` —— 接口通道自动过验证码

`captcha:` 前缀让执行器把"取图 → 识别 → 写变量"合成一步，全程不碰浏览器：

```json
{"名称": "取图形验证码", "method": "GET", "path": "/captcha/get", "no_auth": true,
 "验证码长度": 4,
 "提取": {"验证码": "captcha:data.base64Image",
          "captchaId": "data.captchaId"}}

{"名称": "提交登录", "method": "POST", "path": "/sso/user/login", "no_auth": true,
 "json": {"loginName": "enJnag==", "pwd": "WWIyMDI1IUAj", "userType": "EIAM_USER",
          "captchaId": "${captchaId}", "code": "${验证码}"}}
```

- `验证码长度` 写在同一层，用于校验识别结果位数（不写就不校验）
- 值可以是裸 base64，也可以是 `data:image/png;base64,xxx` 整串，两种都认
- 识别失败时该变量写 `null`，并把步骤判失败，失败原因写明是 `验证码识别失败` —— **不会**把空值当成功
- 引擎缺失（既没 ddddocr 也没 tesseract）时整条用例判 `blocked`，不当缺陷

这条路径比 UI 通道快两个数量级，也不需要浏览器。**能拿到验证码图片接口时优先用它。**

用在数值条件（`长度`、`大于`、`大于等于`、`小于等于`、`期望在`）时会做数值比较，所以可以写"条数等于总数"这类自洽断言，不必把数量写死：

```json
{"名称": "查列表", "method": "GET", "path": "/app/my-app",
 "提取": {"total": "data.total"},
 "断言": [
   {"类型": "JSON字段", "路径": "data.total", "期望在": [1, 200]},
   {"类型": "JSON字段", "路径": "data.records", "长度": "${total}"}
 ]}
```

**提取在同一步骤的断言之前生效**，所以上面这种"用本步骤响应的字段判本步骤的另一个字段"是可以的。

注意区分两类断言：

- 数据规模（`total`、`pages`）随环境变化，用 `期望在` 卡区间；
- 逻辑关系（`records` 条数 = `total`、过滤结果 ≤ 全量）与数据量无关，必须精确断言。

只放宽前者、绝不放宽后者，否则断言就退化成"接口没崩"。

变量没取到值时 `${total}` 不会被静默丢弃，断言会判失败并在报告里显示 `无法解析('${total}')`——比抛异常更容易定位是哪一步提取没生效。

## 写规格的边界

- **一个步骤只验证一个关注点**。一个步骤塞五个断言，失败时看不出到底哪里坏了。
- **预期结果必须能被观测**。"提示友好"不是断言，"响应体含 `1-500`" 才是。
- **不要跨用例共享状态**。用例之间只通过 `依赖` 表达顺序，不靠"上一条用例留下的数据"。
- **写接口必须配 `teardown`**。否则测试环境会被自己的用例污染。
