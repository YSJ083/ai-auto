# 浏览器通道（Playwright 适配协议）

UI 步骤和 HTTP 步骤是**两条并列的通道**，产出同形状的响应，共用同一套断言引擎、结果模型和报告。
所以你会看到：UI 用例也能用 `包含` 断言页面文本，也能被 `compare` 做基线回归，也会出现在同一份通过率里。

---

## 一、什么时候走浏览器

| 场景 | 用什么 |
|---|---|
| 判接口返回对不对 | HTTP 步骤（默认） |
| 判页面上有没有这个按钮、文字对不对、跳转对不对 | UI 步骤 |
| 判点击后的界面变化 | UI 步骤 |
| 判 JS 有没有报错、静态资源有没有 404 | UI 步骤 + `控制台`/`网络` 断言 |
| 判布局有没有错位 | **都别用**，这是视觉回归（截图 diff）的事 |

一条经验：**能被接口断言覆盖的，不要用 UI 断言**。UI 用例单条 2–5 秒，接口单条 30 毫秒，差两个数量级。UI 只用来覆盖"接口测不到的那部分"。

---

## 二、步骤怎么写

UI 步骤用 `ui` 键区分，**不占用 `method`**。带 `ui` 就进浏览器，否则走 HTTP。

```json
{
  "名称": "在账号框输入用户名",
  "ui": "填写",
  "选择器": "input[placeholder='请输入账号']",
  "值": "${env.TEST_USER}"
}
```

### 字段表

| 字段 | 必填 | 说明 |
|---|---|---|
| `名称` | 建议 | 出现在失败信息和截图文件名里 |
| `ui` | 是 | 动作名，见下表 |
| `选择器` | 多数动作必填 | CSS 或 Playwright 选择器，支持 `${变量}` |
| `值` | 填写/选择/按键时 | 支持 `${变量}` |
| `path` / `url` | 否 | 有就先导航。`path` 与 **`base_url`（不含 api_prefix）** 拼接，`url` 用绝对地址 |
| `等待` | 否 | `{"选择器": "...", "超时": 8000}` 等元素；`{"毫秒": 800}` 硬等 |
| `超时` | 否 | 覆盖本步骤超时（毫秒） |
| `第几个` | 否 | 选择器命中多个时选第 N 个（从 0 起） |
| `断言` | 是 | 与 HTTP 步骤同一套校验：没有断言就是没测 |
| `提取` | 否 | 支持 `JSON路径`、`text:正则`、`元素:选择器`、`cookie:名` |

### 页面路径不吃 api_prefix

`path` 只拼站点根，**绝不拼 `api_prefix`**。`/login` 就是 `/login`，不是 `/api/v1/login`。

这条规则犯过一次真实的错：规格里配了 `api_prefix=/common/idaas/v1` 之后，页面被导航到
`http://host/common/idaas/v1/application/myapplication`，返回 404。而当时的断言是
「URL 包含 `/application/myapplication`」——**对那条错误地址同样成立，于是假通过**。
同一条规格里另一条用例报出 3 个 404"缺陷"，其实全是这个拼接错误造成的假缺陷。

现在的防护有两层：

1. 执行器把 `base_url` 与 `base`（含前缀）分开传，UI 通道只拿前者；
2. **导航响应的状态码会被记录**。导航若返回 4xx/5xx 且该步骤没写 `状态码` 断言，
   会自动补一条前置检查判失败，报「导航到 X 返回 HTTP 404 —— 页面本身没打开，后续断言不成立」。
   这条检查排在用例自己的断言之前，报告里第一眼看到的是根因，不是下游连锁失败。

所以：**UI 步骤里 `状态码` 断言是真实有效的**，它读的是主文档导航的 HTTP 状态。

### 动作集

| 动作 | 作用 | 示例 |
|---|---|---|
| `点击` | 点击元素 | `{"ui":"点击","选择器":"button:has-text('登录')"}` |
| `填写` | 清空后输入 | `{"ui":"填写","选择器":"input[name=user]","值":"zrgj"}` |
| `选择` | 下拉框选项 | `{"ui":"选择","选择器":"select#type","值":"1"}` |
| `按键` | 键盘按键 | `{"ui":"按键","键":"Enter"}` |
| `等待` | 等元素出现/消失，或硬等 | `{"ui":"等待","选择器":".loading","状态":"hidden"}` |
| `悬停` | 鼠标悬停 | `{"ui":"悬停","选择器":".menu"}` |
| `滚动到` | 滚动到元素可见 | `{"ui":"滚动到","选择器":"#footer"}` |
| `切换frame` | 后续动作切到 iframe | `{"ui":"切换frame","选择器":"iframe#main"}` |
| `识别验证码` | 取图并 OCR，结果写入变量 | `{"ui":"识别验证码","选择器":"img[src^='data:image/png']","保存到":"验证码","长度":4}` |
| `上传` | 给文件输入框选文件 | `{"ui":"上传","选择器":"input[type=file]","文件":"/Users/me/a.pdf"}` |
| `下载` | 点一下触发下载并落盘 | `{"ui":"下载","选择器":"#export","下载目录":"/tmp/导出"}` |
| `断言快照` | 不做动作，只取页面快照 | 纯断言步骤用这个 |

**`上传` 直接往 `input[type=file]` 塞文件，不做模拟点击。** 站点普遍把 file input
藏起来（`display:none` + label 包装），点 label 会拉起系统文件选择框，自动化里没法操作。
`选择器` 必须指向 `<input type="file">` 本身，指向外层 label 会报"不是文件输入框"。

`文件` 可以是路径、路径数组，也可以用 `${变量}`。文件不存在时当场报错并给出解析后的
绝对路径 —— 相对路径按当前工作目录解析，跨机器跑建议写绝对路径。

**拖拽上传不支持。** 用拖拽实现的站点通常底层还是有一个 file input（往往隐藏），
指向它即可；确实只有 DataTransfer 的站点，这一步只能标 `manual`。

**`下载` 要用一步。** 不要写「导航 + 下载」同一步：那样等的是导航完成，
下载事件还没开始就去做断言了。正确写法是两步：

```json
{"名称": "打开报表页", "ui": "点击", "选择器": "a[href='/report']",
 "等待": {"选择器": "#export", "状态": "visible", "超时": 8000},
 "断言": [{"类型": "URL", "包含": "/report"}]}

{"名称": "导出", "ui": "下载", "选择器": "#export", "下载目录": "/tmp/导出",
 "断言": [{"类型": "下载", "后缀": ".xlsx", "最小字节": 1024}]}
```

`下载目录` 不给时落到 `<输出目录>/下载`。同名文件加 `(2)` 序号，不会互相覆盖。
下载产物按**本步骤窗口**统计，上一个用例下的文件不会混进来。

下载断言、上传的完整写法见 `spec-schema.md` 的「上传与下载」一节。

`断言快照` 很关键：一个步骤做了多个动作、只想在最后断言一次时，用它把断言独立出来。

`识别验证码` 的完整写法与坑见 [6.4 图形验证码怎么自动过](#l3验证码自动识别)。它**没有选择器也能跑** ——
用 `图片地址` 指定一个验证码 URL 即可；两个都不给才报错。

## 三、断言怎么写

### 新增四类

```json
{"类型": "页面", "选择器": "h2", "文本": "我的应用"}
{"类型": "页面", "选择器": ".el-message--error", "可见": true}
{"类型": "页面", "选择器": "tbody tr", "数量": 10}
{"类型": "页面", "选择器": "input[name=user]", "值": "zrgj"}
{"类型": "页面", "选择器": "button.submit", "可用": true}
{"类型": "页面", "选择器": "img.logo", "属性": {"alt": "logo"}}

{"类型": "URL", "包含": "/home"}
{"类型": "URL", "正则": "/detail/\\d+"}

{"类型": "控制台", "无错误": true}
{"类型": "网络", "无失败请求": true, "允许": ["favicon", "/static/png/"]}
```

| 类型 | 判定条件 |
|---|---|
| `页面` | `存在` / `可见` / `数量` / `文本`（包含）/ `文本等于` / `不含文本` / `值` / `属性` / `可用` |
| `URL` | `等于` / `包含` / `正则` |
| `控制台` | `无错误` / `不含`（禁用报错片段） |
| `网络` | `无失败请求`（配 `允许` 白名单放行 favicon 之类的固定 404）；或 `请求` + `次数` / `请求体包含` |
| `下载` | `后缀` / `名称包含` / `最小字节` / `最大字节` / `数量` / `存在`，判的是磁盘上落下的文件 |

### 网络：判到「调了几次、传了什么」

`无失败请求` 只能说明页面没报错，说明不了「点提交真的调了那个接口」。请求级断言：

```json
{"类型": "网络", "请求": "/api/order/submit", "方法": "POST", "次数": 1}
{"类型": "网络", "请求": "/api/user/list", "次数": {"小于等于": 2}}
{"类型": "网络", "请求": "/api/order/submit", "请求体包含": "\"source\":\"h5\""}
```

**只统计本步骤期间**发出的请求（动作前打点），所以「提交只调 1 次」不会被前面
步骤里的同接口调用顶成 2。统计基于浏览器录到的全部响应，明细上限默认 500 条，
可用规格里的 `ui.network_limit` 调大；触顶时这两个判定会**拒绝判定**并说明原因，
而不是拿截断数据给结论。

写这类断言的步骤，快照前会先等「这一步的请求出现」再等它安静下来，预算默认 3 秒
（用步骤的 `网络空闲超时` 调）。这一步是必需的：动作刚结束就取快照，fetch 还没落地，
会把「调了 2 次」读成「0 次」。等不到只记一条诊断，不判失败。

### 页面文本可以直接用 `包含`

因为页面可见文本被放进了响应的 `text` 字段，HTTP 那套断言可以直接用：

```json
{"类型": "包含", "值": ["请输入账号", "请输入密码"]}
```

这条特别适合"表单校验提示"这类多文案断言，比逐条写 `页面` 断言省事。

**但要注意**：页面文本常被空格和换行打碎。比如某系统标题实际渲染成「统 一 身 份 认 证 系 统」（中间有字间距空格），写「统一身份认证系统」会判失败。所以：

- 优先用元素断言，文本断言只写**短词**
- 判文案时选不会带空格的片段，如「忘记密码」「获取验证码」

### `数量` 与 `可见` 的区别

- `数量: 0` 判的是 DOM 里根本没有这个节点。适合判"校验提示未出现"。
- `可见: false` 判的是节点存在但不可见。适合判"弹窗关闭后 DOM 还在、只是隐藏"。

写错了会误判。表单校验提示用 `数量`，弹窗/抽屉用 `可见`。

### UI 步骤没有状态码可断言

`状态码` 断言在 UI 步骤上**只在发生导航时**有意义：它读的是主文档的 HTTP 状态码。

```json
{"ui": "断言快照", "url": "/login", "断言": [{"类型": "状态码", "等于": 200}]}   ✓ 有导航
{"ui": "点击", "选择器": "button", "断言": [{"类型": "状态码", "等于": 200}]}   ✗ 报规格错误
```

第二条会得到：

> 规格错误：这一步没有 HTTP 状态码可断言（UI 步骤且未发生页面导航）。

这是**故意的**。早先版本对没导航的步骤返回 200，那条断言恒为真 —— 一条永远通过的
断言比没有断言更危险，因为它会让人以为验过了。

要确认点击/提交的结果，用 `页面` / `URL` / `网络`；要拿接口状态码，把那次请求单独写成 HTTP 步骤。

> 相关：UI 步骤的 `status` 在 `result.json` 里可能是 `null`。报告会显示
> 「无导航（UI 步骤，不产生状态码）」，不会显示成 `HTTP None`。

### 「无法判定」与「不通过」是两件事

查元素时如果探测本身出错（页面正在跳转、iframe 被卸载、渲染卡住），
引擎**不会**把它报成「元素不存在」，而是：

> 规格错误：UI 断言无法判定：探测元素「.x」时出错（Execution context was destroyed）。
> 这不是元素不存在 —— 常见原因是页面正在跳转、元素所在 iframe 已卸载、或渲染卡住。

区别很关键：

| 报告写的 | 该做什么 |
|---|---|
| 元素「.x」不存在（期望存在） | 查产品：是没渲染，还是选择器过时 |
| UI 断言无法判定：探测元素「.x」时出错 | 查测试时机：加「等待」，别在跳转中断言 |

第二种如果被写成第一种，就会产出一条假缺陷。

## 四、选择器策略

优先级从高到低：

1. **`placeholder` / `name`**：`input[placeholder='请输入您的密码']`。最稳，跟着界面文案走。
2. **`text=`**：`text=登录`、`button:has-text('获取验证码')`。适合按钮，但改文案就失效。
3. **`placeholder` 前缀 + 结构**：`form input:nth-child(2)`。可读性差，尽量别用。
4. **`#随机ID`**：**别用**。Arco / Element 这类组件库的 ID 是运行时生成的，每次都可能变。

一次接入的正确做法：先跑一次探测，把页面上的 `input` / `button` 全列出来，再照着写选择器。不要凭截图猜。

## 五、等待纪律

**不要用固定 sleep。** 用条件等待：

```json
{"ui": "点击", "选择器": "button:has-text('登录')",
 "等待": {"选择器": "text=我的应用", "超时": 8000}}
```

引擎内置的三层等待：

1. 步骤写了 `等待.选择器` → 等它出现/消失（优先）
2. 是导航步骤 → 自动等 `networkidle`（8 秒封顶）
3. 其余 → 只等 `domcontentloaded`（3 秒封顶）

第 2 条很重要：SPA 用 `domcontentloaded` 判定"页面就绪"是不够的，那时 `#app` 还是空的，快照会抓到一片空白，断言就会假失败。所以导航后一定等网络空闲。

如果页面有长轮询/websocket，`networkidle` 永远不满足，会等满 8 秒。这时可以调短超时，别让它每步白等：

```json
{"ui": "断言快照", "url": "/dashboard", "等网络空闲": true, "网络空闲超时": 2000}
```

`网络空闲超时` 单位毫秒，默认 8000。超时**不会**让用例失败，只会记一条诊断（见「七、失败证据」）。

更彻底的办法是给该步骤配 `等待.选择器`，让它压根不走 networkidle 这条路径。

## 六、登录怎么解决

三级策略，详见 `auth-adapters.md` 的 `browser_login` 一节。这里只讲要点：

### L1：复用 storageState（推荐）

```json
{"type": "browser_login", "storage_state": "seeds/state.json",
 "token_from": "localStorage:token", "header": "app-sec-at"}
```

`state.json` 由下面这条命令生成：

```bash
python3 scripts/auto_test.py login spec.json --env test
```

它会打开**可见**浏览器，人工完成登录（含验证码），回车后把整个浏览器态存盘。

### 为什么不能手工拼 state

实测踩到的坑：用已有 token 手写一个 `state.json`，塞进 `localStorage.token` 后，路由守卫是能过的（`tokenValid` 返回 `success:true`，URL 也跳到了 `/application/myapplication`），但 **`#app` 里只有一个空注释 `<!---->`，页面全白**。

在真实登录页上挂钩 `Storage.prototype.getItem` 测出来的实际键（10.31.0.101）：

| 键 | 内容 | 缺了会怎样 |
|---|---|---|
| `token` | JWT，445 字符 | 路由守卫拦回登录页 |
| `userInfo` | 身份、首登标记、gsId | **主布局拿不到用户，`#app` 白屏** |
| `user` | 内嵌 token 的用户对象 | 同上 |
| `route` | 动态路由表，5.4KB | 菜单与页面路由注册不出来 |
| `app` | 主题、布局配置 | 布局初始化异常 |
| `arco-theme` | `auto` | 仅样式 |

**结论：storageState 必须由真实登录产生，不能靠 token 拼。** 这是白屏唯一可靠的解法，也是 `login` 子命令存在的理由。

`login` 子命令现在会把实际拿到的键打出来；只有 1 个键时会直接告警——因为那基本等于"这个 state 一定会白屏"。

### L2：login_steps 自动填表

```json
{"type": "browser_login", "login_url": "/login", "save_state": "seeds/state.json",
 "login_steps": [
   {"ui": "填写", "选择器": "input[placeholder*='账号']", "值": "${env.TEST_USER}"},
   {"ui": "填写", "选择器": "input[placeholder*='密码']", "值": "${env.TEST_PASS}"},
   {"ui": "点击", "选择器": "button:has-text('登录')"}
 ],
 "success": {"类型": "URL", "包含": "/application"},
 "token_from": "localStorage:token", "header": "app-sec-at"}
```

`success` 是登录成功的判定条件，用同一套断言语法。判不过会抛 `AuthError`，并带上**当前页面地址和文本片段**，便于分辨是账号错、验证码错还是别的问题。

### L3：验证码（自动识别）

验证码由 `core/captcha.py` 处理，两条通道都接了：

| 通道 | 写法 | 说明 |
|---|---|---|
| UI | `{"ui":"识别验证码","选择器":"img[src^='data:image/png']","保存到":"验证码","长度":4}` | 取图 → OCR → 写变量 |
| HTTP | `{"提取":{"验证码":"captcha:data.base64Image"}}` | 直接从响应体取 base64 → OCR |

然后再用 `${验证码}` 填进输入框，或直接放进 `json` body。**全程无人工**。

#### 引擎选择

三级降级，探测顺序固定：

1. **ddddocr**（首选）—— 针对验证码训练，彩色、扭曲、干扰线都能认
2. **tesseract** —— 通用 OCR，靠 Pillow 预处理救回来一点（多阈值二值化）
3. 都没有 —— 抛 `CaptchaUnavailable` → 该用例判 **`blocked`（环境问题）**，不算缺陷

判 `blocked` 而不是 `failed` 是刻意的：**装不上 OCR 是测试环境的问题，不是被测系统的缺陷**。

#### 取图的两个坑

- **不要截图**。验证码原图 200×100，页面渲染成 64×32，截图后再放大是插值出来的假像素，
  OCR 准确率断崖下跌。优先读 `<img>` 的 `src` 里那段 `data:image/png;base64,`，
  解出来就是原始字节；只有 `src` 拿不到（比如走了网络 URL 且需要鉴权）才退化成截图。
- **`tesseract` 不要直接转灰度**。该系统的验证码每个字符一种颜色，黄色 `(255,255,0)`
  和浅蓝 `(120,200,255)` 转灰度后几乎等于白底，会直接丢掉这些字符（实测 4 位只认出 2 位）。
  正确做法是取 `min(R,G,B)`（`ImageChops.darker`），把所有彩色都压成深色。

#### 准确率与重试

实测目标系统（4 位字母数字）：ddddocr 标准模型约 **80%**，beta 模型约 73%，tesseract 约 **20%**。

所以**验证码用例必须配重试**，这是物理规律不是补丁：

```json
{"id": "TC-LOGIN-001", "重试": 5, "steps": [...]}
```

5 次重试 = 6 次尝试，按 80% 单次成功率算，整体成功率约 99.99%。
实测（无重试）首轮 5/6 ≈ 83%；配 5 次重试后 5/5 全部通过。

#### 三条实测结论，别踩

1. **这个验证码不区分大小写**。`slkQ` 和 `slkq` 等价。所以"用大小写变体去碰撞"完全没用。
2. **captchaId 一次性**，提交失败立即失效（返回 `验证码失效`）。所以"同一张图换个写法再试"
   这条路是死的，只能重新取码 —— 这就是用例级重试的作用。
3. **误差几乎全是字符认错**（`O/0`、`l/1`、`S/5`），不是大小写。想提高准确率要往字符集收敛上使劲。

#### 长度校验

`长度` 字段是可选的，但强烈建议写。ddddocr 在字符粘连/断裂时会少吐或多吐一位，
这种结果拿去提交**必定失败**，还会白白消耗一个一次性的 captchaId。
写了 `长度` 之后，长度不符会先用 tesseract 交叉验证，仍不符就**原地抛 `CaptchaError`**，
快速进入重试，不做无意义的提交。

#### 排查开关

```bash
# 打验证码识别结果
AUTOTEST_CAPTCHA_DEBUG=1 python3 scripts/auto_test.py run spec.json
# 额外把识别用的图存到 /tmp
AUTOTEST_CAPTCHA_DEBUG=save python3 scripts/auto_test.py run spec.json

# 只追踪关心的接口（逗号分隔的 URL 子串）
AUTOTEST_CAPTCHA_DEBUG=1 AUTOTEST_TRACE_URLS=/sso/user/login,/captcha/get \
  python3 scripts/auto_test.py run spec.json
```

`AUTOTEST_CAPTCHA_DEBUG=1` 会打印页面发出的请求与响应。追踪范围由
`AUTOTEST_TRACE_URLS` 决定；**不设时默认只打「非 GET 请求 + 4xx/5xx 响应」**。
早先版本把登录接口路径写死在代码里，换系统就失效，现在不会再绑定任何具体地址。

排查"到底是验证码错了还是断言写错了"时特别好用 —— **这一点值得强调**：
曾经有一轮排查把"断言字段名写错（`不包含` 应为 `不含`）"误判成"验证码一直过不去"，
因为两者在报告里都表现为登录测试失败。打开这个开关，看响应体里有没有 `data.at`，
一眼就能区分。

#### 不要用它做什么

- **别拿它测"验证码本身对不对"**。它测的是"带验证码的登录链路能不能走通"。
- **别把 OCR 认错记成产品缺陷**。识别错会返回 `验证码错误`，看起来像缺陷，其实是我方误差。
  用例配了重试就能吸收掉；如果重试用尽仍失败，优先怀疑识别，而不是先提缺陷单。

## 七、失败证据

UI 步骤断言失败时自动整页截图，存到 `<结果目录>/截图/<用例id>--<步骤名>.png`，路径写进 `result.json` 的 `steps[].screenshot`。

截图是**失败当时**的页面，不是事后补的 —— 所以能直接看出"点完之后页面停在哪"。

`控制台` 和 `网络.无失败请求` 的采集是**累积的**：从浏览器会话打开到当前步骤，所有 JS 错误和失败请求都记着。语义是"到目前为止页面出过错"。如果你只想判某一步范围内的，把它写成用例的最后一步。

请求级统计（`请求` + `次数` / `请求体包含`）不一样，**按步骤算**：只数本步骤动作期间发出的请求。两者口径不同是有意的 —— 前者问"整轮有没有出过错"，后者问"这一步到底调了什么"。

### 证据没采到时会明说

采集、等待环节出问题时（截图存不下、登录态写不成、cookie 注不进去、
事件监听器没挂上、networkidle 超时），引擎**不会**静默放过，也不会让用例失败，
而是记一条诊断，随 `result.json` 的 `steps[].diagnostics` 落盘，并在报告里多一节：

> **八、采集诊断（不影响用例判定）**
>
> | 现象 | 涉及用例 | 细节 |
> |---|---|---|
> | 失败截图没能保存（TC-1--提交登录.png） | TC-1 | FileExistsError: ... |

它**不改变任何用例的通过/失败判定**，但看结论时要打折扣 —— 尤其这两种：

| 诊断 | 为什么严重 |
|---|---|
| 事件监听器未能全部挂载 | `console_errors` 恒为空，`{"类型":"控制台","无错误":true}` 会永远通过 |
| 失败截图没能保存 | 报告里截图位空白，看起来像"页面本来就长这样" |

页面文本也不是每步都采：只有用例里出现文本类断言（`文本`/`文本等于`/`不含文本`，
或 `包含`/`不包含`）才读整页 `innerText`。没采时报告写「本步骤未采集页面文本，属正常省略」，
不会留一个空代码块让人误以为页面是空的。

## 八、环境档配置

```json
{"profiles": {
  "test": {
    "base_url": "http://10.31.0.101",
    "ui": {
      "headless": true,
      "timeout": 20000,
      "browser": {"channel": "chrome"},
      "viewport": {"width": 1440, "height": 900},
      "slow_mo": 0,
      "network_limit": 500
    }
  }
}}
```

`network_limit` 是单次会话最多记录多少条请求明细（默认 500）。请求级的
`次数` / `请求体包含` 断言依赖这份明细；页面首屏请求特别多、报「记录被截断」时调大它。

`browser` 三种写法：

| 写法 | 含义 |
|---|---|
| `{"channel": "chrome"}` | 用系统装的 Chrome，**0 下载**，推荐首选 |
| `{"executable_path": "/path/to/chrome"}` | 用指定二进制 |
| `{"bundled": true}` | 用 Playwright 自带浏览器，需先 `playwright install chromium` |

不配时自动按「系统 Chrome → 缓存 chromium → 自带」顺序探测，启动信息里会打印实际用的哪个。

`slow_mo` 是排错用的（每步放慢多少毫秒），**不要**在生产回归里开。

## 九、排错表

| 现象 | 原因 | 处置 |
|---|---|---|
| `未安装 playwright` | 依赖没装 | `pip install playwright` |
| `浏览器启动失败` | 三个来源都没找到 | `playwright install chromium`，或配 `executable_path` |
| 页面快照全空、断言全失败 | 导航后没等渲染 | 给步骤配 `等待.选择器`，别用 `domcontentloaded` 硬判 |
| `选择器不存在` 但肉眼可见 | 元素在 iframe 里 | 前面加一步 `{"ui":"切换frame","选择器":"iframe#x"}` |
| `选择器不存在` 且元素是动态渲染 | 快照抓早了 | 同上，加等待条件 |
| `控制台无错误` 一直失败 | 有历史遗留 JS 报错 | 用 `不含` 精确排除已知无害报错，别整体关掉 |
| `网络无失败请求` 一直失败 | favicon、埋点脚本 404 | 用 `允许` 白名单，白名单只放固定 URL 片段 |
| `记录被截断，拒绝判定` | 单会话请求数超过 `network_limit` | 调大 `ui.network_limit`，别把这条当失败 |
| UI 步骤写了 `轮询` | 轮询只支持 HTTP 步骤 | 改用 `等待.选择器`（Playwright 的条件等待已经够用） |
| 同一用例时而通过时而失败 | 渲染竞态 | 加等待条件；仍然 flaky 就说明是真实的时序缺陷 |
| `规格错误：这一步没有 HTTP 状态码可断言` | 在没导航的 UI 步骤上写了 `状态码` 断言 | 改用 `页面`/`URL`/`网络`；要状态码就拆成 HTTP 步骤 |
| `UI 断言无法判定：探测元素…时出错` | 探测时页面在跳转 / iframe 已卸载 | 加 `等待.选择器`；这不是元素不存在，别当缺陷提 |
| 每步都慢 8 秒 | 页面有长轮询，`networkidle` 等不满 | 配 `网络空闲超时: 2000`，或改用 `等待.选择器` |
| 报告里截图位置空白 | 截图没存成 | 看「采集诊断」一节的具体原因，别当成页面本来如此 |
| storageState 加载后页面空白 | state 是手工拼的 | 用 `login` 子命令重新生成 |
| 页面 404，URL 里多出接口前缀 | `path` 被拼上了 `api_prefix` | 老版本的 bug，已修；若复现，检查是否有代码用 `ctx["base"]` 拼页面地址 |
| 报告里一串 404，但地址都带 `/common/idaas/v1/xxx` | 同上，导航地址错 | 同上；这类"缺陷"先怀疑路径拼接，别急着报给开发 |

## 十、常见误用

- **拿 UI 用例替代接口用例**。界面全绿不代表接口全对，反过来也一样。两层各测各的。
- **用固定 sleep 等渲染**。慢的机器上照样失败，快的机器上白等。
- **选择器用运行时生成的 ID**。改一次版本全部失效。
- **断言写长句页面文本**。空格、换行、标点任一变化就假失败。
- **把 `控制台` 断言放在第一条用例里**，后面的用例继续继承前面攒下的错误。要么单独开一条用例只测前端健康度，要么接受"累积"语义。
- **开了 `slow_mo` 还拿结果算性能**。那是排错模式，不是真实耗时。
